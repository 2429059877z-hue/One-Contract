## 一、动作模型

动作选择的核心问题是：是否能在不虚构事实的前提下形成负责任、可执行的正文方案。

| 证据状态 | 默认动作 | 例外方向 |
|---|---|---|
| `confirmed` | 直接修订 | 重大修改附简短批注；纯格式不附批注 |
| `reasonable_assumption` | 修订加批注 | 默认文本会误导时改为仅批注 |
| `major_choice` | 仅批注并升级 | 用户作出选择后，将证据状态更新为 `confirmed` 再修订 |
| `not_applicable` | 不输出 | 需要解释排除理由时只记内部日志 |

不要用风险描述中的关键词自动决定动作。review plan 应显式给出证据状态、方案和假设。

## 二、直接修订

以下情形通常可以直接形成正文：

- 原文存在明确的法律、逻辑、结构或执行问题；
- 不需要创造金额、日期、状态或当事人共识；
- 可以通过条件句、占位符、定义或程序机制承载暂缺变量；
- 当前立场下存在一个有充分理由的专业默认；
- 通知、付款、验收、证据、救济、交接或存续机制可以补齐；
- 相邻条款的影响能够同步处理。

多个写法都可接受，不妨碍选择一个专业默认。正文修订是可见、可拒绝和可回退的建议，不要求所有事实都达到诉讼证明标准。

**正文只含确定主方案**：可直接落笔的正文修订只放确定、可签署的主方案文本。以下三类内容一律进批注，不进入正文：

- 待核实前提（如“如目标公司章程另有要求”）；
- 事实假设（如“如标的股权存在未届期认缴出资”）；
- 建议性表述（如“建议将激励份额授予安排在…”）。

正文允许的条件句是合同机制本身（如“乙方逾期超过30日，甲方有权解除”），不是审查者提请注意的前提。涉税内容按 `【涉税建议】` 统一进意见书，正文修订中不夹带税务判断。

## 三、修订加批注

能提出主要方案但存在待核变量时，正文先给完整机制，批注只说明：

1. 当前采用的事实假设；
2. 需要谁确认什么；
3. 确认结果会如何改变文本；
4. 必要时的一项备选路径。

适用场景包括金额/日期/附件待填、主方案与备选方案并存、修改幅度较大、重大风险先给保护性文本、或最终强度需要客户确认。

## 四、仅批注

仅在无法负责任地选择具体文本时使用：

- 缺失事实会改变法律结论，而条件句也无法避免误导；
- 方案实质互斥，必须由客户作商业选择；
- 文本会确认未经核实的收讫、验收、无争议、权利放弃或历史事实；
- 担保、知识产权归属、排他、控制权、责任上限等结构决定缺少授权；
- 关键附件、许可、审批或外部协议缺失；
- 可能存在工伤、职业病、欺诈、胁迫或重大合规事件，普通条款可能掩盖风险。

仅批注不是回避判断。批注仍应说明冲突、选择标准、推荐方向和下一步。

## 五、最小必要修订

按下列顺序寻找最小、完整的动作：

1. 删除造成风险的一小段；
2. 补入触发条件、边界、通知、证据或例外；
3. 替换局部短语或机制节点；
4. 在稳定不变片段之间形成数个成组修订块；
5. 只有原条款整体失效时才整条重写。

“最小”以解决机制为单位，不以字数最少为目标。只替一个词却留下付款、验收或救济断裂，不是合格的最小修订。

不要为了显示工作量统一所有措辞，也不要制造十几个单字级修订。复杂修改通常收敛为 2—6 个能被人理解的修订块。

## 六、重大修改与谈判阻力

重大修改先检查：

- 是否改变交易价格、控制权、责任范围或退出权；
- 是否与附件、订单或内部流程冲突；
- 是否会让对方误以为我方否定交易；
- 是否存在保护效果相近但阻力更低的变体；
- 是否应分为首选、底线和可交换条件。

重大修改可附批注解释原因，但不把完整法律论证塞入边栏。谈判清单负责排序，正文负责给方案，报告负责解释。

## 七、批注写法

推荐四句以内：

> 现按【假设】形成主方案。请确认【事实/授权】；若【另一结果】，则改为【方向】。本修改影响【付款/退出/责任等】。

避免：

- 复制整段正文；
- 只写“存在风险”“建议修改”；
- 把未核事实写成陈述句；
- 给出与正文不同的金额、期限或机制；
- 堆砌法条原文和长篇论证。

## 八、review plan 字段

建议 finding 使用以下语义字段；执行器只实现计划，不替代法律判断：

```json
{
  "id": "F-001",
  "risk_level": "P1",
  "evidence_state": "reasonable_assumption",
  "action": "replace",
  "target_text": "<原文定位>",
  "replacement_text": "<可直接落文的主方案>",
  "assumptions": ["<当前假设>"],
  "unknown_facts": ["<待确认事实>"],
  "comment": "<假设、待确认项和替代方向>",
  "linked_clauses": ["<联动条款>"],
  "basis_type": "legal_boundary|practice|risk_control|negotiation|client_policy|independent_judgment"
}
```

`action=auto` 只根据显式证据状态和是否存在改文载荷分流，不扫描风险文字中的关键词。显式 `comment/delete/insert/replace/report-only` 优先。

## 九、复核清单

- 所有能落文的重大事项是否真正进入正文；
- 批注是否只承载事实、授权、选择和重大不确定性；
- 是否存在未知事实被写成既成事实；
- 每项重大修订是否处理相邻条款；
- 修订密度是否与风险和谈判阻力相称；
- 接受修订后的正文是否是完整、可执行的合同；
- 批注、报告和正文是否采用同一方案；
- 失败项是否在日志和报告中可见；
- 缺失信息是否统一用 `【待填：事项】` 式样、只做一处汇总批注，且未因“待填”误升级为 P0/P1；
- 正文是否只含确定主方案，未混入待核实前提、事实假设或建议性表述；
- 意见书末尾是否含 `【待填事项汇总】` 与 `【涉税建议】` 两区块，且未写 DOCX/质量门等技术披露。

## 十、缺失信息的统一标记

当事人姓名、价款、日期、账户、联系方式等后续会补的信息，属于“待填”而非结构性风险。统一处理：

- **统一式样**：正文用 `【待填：事项】` 标记，如 `【待填：乙方姓名】`、`【待填：签署日期】`、`【待填：第一笔付款期限】`。同一式样用于全部缺失项，不混用 `【　】`、下划线或纯空格。
- **只做一处汇总批注**：在文首或首次出现处加一条批注，列出全部 `【待填】` 项；正文不再逐项批注。
- **不因“待填”升级风险**：单纯待填信息不单独标为 P0/P1，风险等级只反映真实交易风险。只有缺失会改变法律结论或授权边界（担保、权利放弃、控制权、责任上限、外部审批等）时才升级，且说明为什么该项待填会改变结论。
- **意见书**：审查意见书末尾设 `【待填事项汇总】` 区块，列出全部 `【待填】` 项与后续填写动作。

条件句、程序机制等其他占位手段不在此列，仍按对应规则处理。
