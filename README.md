# One-Contract

面向律师、法务和合同高频处理团队的**原则型、修订优先、可验证**合同审查与起草 Skill。

它最大的特点是一套**接近资深律师带教的工作流程**：先理解交易目的和事实缺口，再按证据状态决定落笔方式，把能负责任落文的方案写成真实 Word 修订，把事实、授权和重大选择交给批注，最后用严格质量门验证交付文件——而不是堆叠规则命中或输出一份风险报告。

> 目标不是堆叠规则命中或风险报告，而是交付可接受、可拒绝、可回滚、可验证的合同修改。

---

## 一、核心工作流程（7 步）

这是 One-Contract 区别于其他合同审查工具的核心。它把"律师怎么审合同"变成一套可执行、可追溯、可回归的方法。

```
① 保全输入   ② 证据账本   ③ 宽识别推理   ④ 形成方案
      →            →            →            →
⑤ 审查计划   ⑥ DOCX 执行   ⑦ 一致性复核
      →            →            →   交付
```

### 第 1 步：保全输入，建立审查上下文

- 在**副本**上操作，保留原件及哈希，原件永不改动；
- 明确我方身份、核心交易目的、审查阶段、主要底线和现实议价能力；
- 企业合同先输出**稳定合同画像**：主类型、辅类型、文档性质、我方角色、场景标签、分类置信度、所需原则卡与模块；
- 只有标题、交易结构和当事人角色一致且分类高置信时才自动路由；中低置信、混合交易或角色不明时**先确认，不自动路由**。

### 第 2 步：建立事实与证据账本

把每个关键事项标为四类**证据状态**——这是决定"怎么落笔"的开关：

| 证据状态 | 含义 | 默认动作 |
|---|---|---|
| `confirmed` | 材料足以支持事实和动作 | **直接修订**（重大事项附简短批注）|
| `reasonable_assumption` | 可提出主要方案，但需公开假设 | **修订＋批注**（说明假设、待确认事实、替代路径）|
| `major_choice` | 事实或授权会改变结构性方案 | **仅批注并升级**；用户选择后再修订 |
| `not_applicable` | 已有事实足以排除 | 不输出，必要时记录内部理由 |

- 金额、日期、支付状态、验收状态、收讫、无争议、权利放弃及外部审批**不得靠推测补齐**——用占位符、条件句、程序机制或批注保留未知变量；
- 缺失或待填信息统一用 `【待填：事项】` 标记，只做**一处汇总批注**、不逐项批注、不因"待填"单独升为 P0/P1；仅当缺失会改变法律结论或授权边界时才升级。

### 第 3 步：宽识别并重新推理

- 从**交易结构、合同文件体系、条款机制**三层识别问题——复杂事实决定动作强度，不决定是否分析；
- 对每个实质问题回答六问：保护什么利益 / 什么事实改变判断 / 当前立场下的专业默认 / 什么足以推翻默认 / 与哪些条款联动 / 属于法律底线、实务倾向还是谈判策略；
- 获取该类型的 `active` 原则卡和条款模块后，**结合具体交易重新推理，不做整份模板差异替换**；
- **联动组必查**：付款与验收、解除与违约、结算与权利终结、保密与知识产权、限责与赔偿。

### 第 4 步：先形成正文方案，再选择动作

优先问"能否在不虚构事实的前提下形成专业文本"，而不是"所有事实是否已经齐全"。

- **正文只含确定主方案**；待核实前提、事实假设、建议性表述一律进批注；
- 能通过局部删除、补入或替换解决时，不整段重写；局部动作制造碎片时才成组修订；
- 修改密度由风险、文本质量、交易阶段、我方立场和谈判阻力共同决定——不为了展示工作量修改无关措辞，也不因"克制"把可落文的重大事项退化为批注。

### 第 5 步：形成审查计划（review plan）

每个 finding 至少写明：稳定 ID、条款位置、风险等级、事实依据与证据状态、保护利益与判断理由、动作类型、目标文本与可直接落文的文本、未知事实与假设、必要批注、法条依据。生成计划时**先检查 finding 之间是否冲突**，再交给执行器。

### 第 6 步：应用并验证 DOCX

```
apply_review_plan.py 执行（真实 w:ins / w:del 修订 + 批注）
        ↓
quality_gate.py 质量门：
  1. ZIP 与全部 XML/RELS 解析
  2. 编码、关系、content types、批注锚点检查
  3. 生成"接受全部修订"与"拒绝全部修订"两个副本
  4. 最终文本与审查计划覆盖核对
  5. LibreOffice 渲染并逐页检查 PNG
```

**执行器返回 0 不等于完成**。任一硬门失败，审阅件不得作为最终交付。

### 第 7 步：一致性复核与交付

- 核对原文、修订稿接受视图、批注、审查意见书和执行日志的一致性；
- 所有失败项必须出现在执行日志和对外报告的适当位置，**不得静默遗漏**；
- 交付物：审核修订版 DOCX（真实修订＋批注）、与修订稿一致的审查意见书 DOCX，内部留存 review plan、执行日志、接受/拒绝副本和质量门报告；
- 高风险法律结论、事实争议和对外发送前**保留律师终审**。

## 二、为什么这样工作：三层分工

```
┌──────────────────────────────────────────────┐
│  Agent（模型）                                 │
│  理解交易 → 识别风险 → 形成方案 → 复核交付      │
├──────────────────────────────────────────────┤
│  Knowledge（知识资产）                         │
│  原则卡/条款模块/触发器/经验卡（仅 active 加载）│
│  + 通用条款原则（底线兜底）                    │
├──────────────────────────────────────────────┤
│  Scripts（执行器）                             │
│  review plan → DOCX 真实修订/批注 → 质量门验证  │
└──────────────────────────────────────────────┘
```

- **Agent** 负责专业判断：识别风险、形成审查计划、推荐措辞、复核一致性；
- **Knowledge** 提供专业起点：原则卡只给判断坐标、默认倾向、推翻因素和硬边界；条款模块只给结构、前提和可接受变体——不锁死为固定答案；
- **Scripts** 承担确定性技术工作：在 DOCX 中稳定写入修订和批注、执行质量门，减少复制粘贴导致的格式错误。

**通用条款原则与专项资产的关系**：跨类型通用条款（管辖、付款节奏、通知送达、合同变更等）由通用原则统一处理；专项合同类型资料在通用原则的**硬边界内深化**该类型的审查。专项的场景化深化优先，但不得突破法律与动作边界（不虚构事实、不单方改写有效管辖、不越过强制标准）。

## 三、当前覆盖范围

采用**企业合同分类体系 v2**（EC-01 ~ EC-10，永久 `type_id`）。首批 20 个类型中，已有 **5 个类型正式激活**（`active`，可直接用于正式审查）：

> 说明：本包内 `references/contract-types/` 下的 12 类目录为 **v1 遗留参考资料**（买卖、租赁、服务等旧分类），仅作未激活类型的兜底参考，**不代表当前正式分类体系**。正式分类以 v2 的 EC-01 ~ EC-10 为准。

| 类型 | 状态 | 资产 |
|---|---|---|
| 股权转让（EC-01-001） | ✅ 已激活 | 原则卡 + 8 模块 + 触发器 + 经验卡 + 联动组 |
| 设备、原材料采购（EC-02-002） | ✅ 已激活 | 原则卡 + 5 模块 + 触发器 + 经验卡 |
| 协商解除劳动关系（EC-06-004） | ✅ 已激活 | 原则卡 + 5 模块 + 触发器 + 经验卡 |
| 员工保密（EC-06-002） | ✅ 已激活 | 原则卡 + 5 模块 + 触发器 + 经验卡 |
| 竞业限制（EC-06-003） | ✅ 已激活 | 原则卡 + 5 模块 + 触发器 + 经验卡 |

其余类型保持候选框架。运行时通过 `select_active_assets.py` **只加载 `active` 资产**；没有激活资产时按通用原则型方法审查，并明确"暂无成熟母版"，不把候选资料包装成正式知识。

支持：甲方/乙方/中立等立场、克制/常规/强势等口径、仅批注/直接修订/批注修订结合等落痕策略、DOCX 原生批注/修订/Word 审查意见书。

### 劳动人事专项

协商解除、员工保密、竞业限制三类已深度激活，覆盖：经济补偿依法与提出方判断、结算分项与程序义务、保密范围与岗位匹配、资料返还/删除/账号退出、竞业主体适格与期限≤二年，并严格区分**法律强制边界**（期限、适格人员、按月补偿）与**指引建议**（人社部竞业合规指引的补偿/违约金比例，非强制）。

## 四、安装方式

1. 打开本仓库的 GitHub Releases。
2. 下载最新版本的 skill 压缩包。
3. 解压后将 `one-contract/` 文件夹放入你的 skill 目录。
4. 在支持 `SKILL.md` 的 Agent / Claude 环境中启用该 skill。
5. 如需生成 Word 批注、修订或报告，安装脚本依赖：

```bash
pip install -r scripts/requirements.txt
```

首次生成审查文件时，按 Agent 提示确认审查人姓名和机构；配置会写入本地 `config/`，不会作为公开发布内容使用。

## 五、可以怎么用

- "站在采购方立场，以常规口径审查这份设备采购合同"
- "帮我把服务合同里的验收、付款和违约责任条款补齐"
- "请输出审查报告，并把确定性问题直接修订进 Word"
- "我要起草一份技术开发合同，请先列起草信息清单和待确认问题"

## 六、使用边界

**适合**：中文商业合同的常规审查、起草和交付格式统一；批量合同的一轮风险扫描和修订底稿生成；律师或法务复核前的结构化整理。

**不适合**：替代律师对重大交易作最终签署意见；处理未提供事实背景、交易安排或业务目标的合同；覆盖所有涉外法域、外文合同和高监管行业专项审查；自动完成需要线下审批、登记、备案或主体授权核验的事项。
